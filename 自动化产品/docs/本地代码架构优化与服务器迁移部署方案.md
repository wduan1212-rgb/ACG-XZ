# 本地代码架构优化与服务器迁移部署方案

记录日期：2026-08-03

状态：**生产已受保护完成 `137003`→`140004` 并运行 v140 `9e8aeb5`，现有团队、资源 scope、媒体 registry 和持久文件为唯一生产事实。当前本地候选保留所有已完成门禁，只增量引入 expand-only `140005`、hydration/compose 收敛、供应商交付媒体精确读和视频工坊成片发布修复。它尚未部署、未写生产；下一次部署只能从审计后的唯一提交建立新 release，并用 fresh v2 备份绑定单独双跑 `140005`，禁止重做前七步或用本地数据/媒体覆盖生产。**

本方案以当前 v140 候选和已记录的生产受保护切换证据为依据。生产为 Ubuntu 24.04 / Python 3.12.3 / FFmpeg 6.1.1；主服务和回环 8765 sidecar 已以 release/持久数据边界运行 v140。SQLite、约 15 GB 受保护媒体、用量 spool、视频 runtime、环境和认证状态均不随代码切换。`/api/health` 只证明存活；是否可写只看受保护 readiness 中的 `writeReady`。

## 1. 当前架构判断

### 1.1 应保留的边界

- 主平台继续作为唯一公网入口，负责身份、租户、配额、资产、社区、供应商和任务登记。
- 视频工坊继续作为仅监听回环地址的 sidecar；不要把其依赖和媒体流水线合并回主进程。
- 静态视频继续走图片分镜、可选 TTS、字幕/BGM 与本地合成链路，不进入 Seedance；分镜按语义及存在的口播自然拆分，只要求整体时长大致合理，不建立精确时长约束，也不强制用户提供或生成口播。
- 无限画布继续保持“React 源码 + 审计后的静态闭包 + 同源 iframe”边界；服务器运行只读取静态闭包，源码用于重建和审计。
- SQLite、uploads、composed、canvas blobs、视频工坊 runtime、模型缓存、环境变量和认证状态均属于持久数据或私密配置，不进入代码发布包。

### 1.2 当前主要风险

| 风险 | 当前证据 | 影响 |
| --- | --- | --- |
| 主服务与存储层仍过度集中 | 鉴权、团队、供应商、计费、媒体和迁移仍集中在 `server/main.py` / `server/store.py` | 后续应按域机械拆分，不在迁移 release 同时改 API 或数据形状 |
| 模型用量生产账本仍不完整 | v139 本地已统一主服务/画布/视频工坊的逐次 attempt receipt、spool/outbox 与 `role=user` 汇总；生产 v120 指定 editor 仍有成功项目而中央用量为 0 | 0 不能解释为未使用；部署前须在生产副本验证 `139001`、历史证据下限恢复、幂等对账和同盘性能，未知 token 不得猜补 |

## 2. 目标架构

目标不是一次性重写，而是在保持现有 API、数据库和媒体 URL 可读的前提下逐步拆分。

```text
Browser / Desktop Client
        |
        v
Main API (8787, single public entry)
  ├─ routers: auth / teams / supplier / assets / community / canvas / video
  ├─ policies: TenantContext / AuthPolicy
  ├─ services: Billing / UsageReceipt / AssetRegistry / Community / CanvasCheckpoint / Job
  ├─ repositories: users / teams / documents / tasks / media
  ├─ migrations: numbered, checksum, forward-only
  └─ readiness: release + schema + data paths + sidecar + vendor manifest
        |
        ├─ SQLite (current transactional source of truth)
        ├─ protected media directories / future object storage
        └─ Video Workshop sidecar (8765, loopback only)

Infinite Canvas
  source -> reproducible build -> manifest -> audited vendor closure -> iframe
```

### 2.1 v137–v140 已实现的安全层

- 生产环境在 store 导入前解析，普通启动为 validate-only；主服务和 sidecar 均有服务端强制只读。
- 迁移为前向编号和 checksum/status 账本：`137003` schema、`137004` ACG 团队数据、`139001` usage receipt/outbox、`140001` 资源 scope schema、`140002` 历史资源归属、`140003` 私有媒体 schema、`140004` 历史媒体归属、`140005` 视频 compose 幂等 schema。
- `140002` 要求每条历史资源获得唯一 scope；真正 unresolved/ambiguous 为硬阻断，只在已有唯一归属证据时将陈旧次要引用记为 warning。极少数无自动证据记录可在 writer 冻结的维护窗生成精确人工复核 manifest；它必须绑定 database identity/路径摘要/逻辑摘要/schema/user version 与 fresh backup manifest SHA，preflight 和 apply 使用同一文件/备份并在事务内重验，不允许模糊默认归入 ACG。
- `140004` 不改文件名和 URL。无引用孤立文件 quarantine 保留但不开放；被业务引用却缺 owner、缺文件、多 owner 或 team 冲突都在零 registry 写入前阻断。
- 所有 apply 都要求紧接其前创建的 `acg-sqlite-backup-v2`，并在同一 `BEGIN IMMEDIATE` 重新比对 source inode identity、路径摘要、schema/user version 和逻辑摘要；前一步成功后必须重新备份，不得复用 manifest。
- `/api/ready` 在 RO 模式允许旧但完整的 v120 库进入迁移验收，同时清楚显示 `writeReady=false`；RW 启动在提供 socket 前必须通过 schema、137004、140002、140004、usage spool/outbox、路径、sidecar、画布、release 和媒体 coverage 全部门禁。
- release verifier、两份精确依赖 lock、目标 ABI wheelhouse manifest 与完整 runtime snapshot/verify/restore-drill 工具均已本地实现。

上述是本地安全机制，不是生产验收证据。

### 2.2 尚未解除的生产门禁

1. **生产副本尚未双演练**：必须用新的在线一致副本按 7 个版本号连续执行，第二轮零新增/零重复，且稳定 ID、凭据、业务计数和媒体 inventory 不异常漂移。
2. **权限与媒体实数尚未出具**：`140002` 后资源 scope 必须为 100%，`140004` 后所有可开放媒体必须有唯一 owner/team；任何 unresolved、ambiguous、missing referenced owner/file 或 registry conflict 都不能用 warning 绕过。
3. **完整冻结恢复须从修复后提交重做**：`927bd29` 的生产形状隔离演练已验证 6,713 个媒体文件无缺失、无多余且内容/大小一致，但 6,688 个文件的恢复 mtime 最多漂移 120ns，使精确媒体摘要无法闭环。restore-drill 现按 manifest 恢复并严格复核每个普通文件的 `mtimeNs`，目标文件系统发生任何舍入都 fail closed；必须从新提交重做 complete snapshot、恢复和第七步 preflight。
4. **离线环境尚未在正式目标主机封板**：主服务与 sidecar 的 wheelhouse 必须针对生产 Python/ABI 构建、验签、离线安装到新 venv，再用精确 lock 拒绝缺包、版本漂移和额外包。
5. **usage 恢复/性能和兼容回滚仍待证明**：`139001` reconciliation、历史 evidence manifest、64/128 路 receipt 门禁以及理解 v140 schema/租户语义的前向回滚 release 都必须在生产形状副本通过。原始 v120 不是迁移后代码回滚目标。

### 2.3 P1：降低耦合

- 将 `server/main.py` 拆为 `api/auth.py`、`teams.py`、`supplier.py`、`assets.py`、`community.py`、`canvas.py`、`video.py`；旧路径先作为兼容适配器，不同时改调用方和存储结构。
- 将 `server/store.py` 拆为 repositories 与 services。路由只负责参数、鉴权和响应；事务由服务层拥有。
- 建立统一 `BillingService` 与不可变结算流水，图片、TTS、音色、动态/静态视频都只通过同一 reserve→settle/release 协议。
- 建立 `UsageService`：主服务为每次模型操作签发稳定 operation/member/team 身份，主服务和 sidecar 产出同一 receipt 形状；成功创作与遥测写入解耦，但失败 receipt 必须落入持久 outbox 重试和告警，不能继续静默丢失。
- 建立 `AssetRegistry`，记录 owner/team、对象 hash、MIME、大小、来源任务和状态；现有文件路径与 URL 继续双读，逐步回填，不做一次性搬库。
- 视频任务改为持久任务表、lease、heartbeat 和明确终态。完成前保持单 worker，避免多个 worker 绕开进程内并发门。
- iframe `postMessage` 增加 `protocolVersion`、capability handshake 和向后兼容分支。

### 2.4 P2：长期演进

- 通用 documents JSON 按域使用 shadow write、dual read、回填校验逐步迁入显式表；确认一致后才切读，禁止一次性大迁移。
- 增加事务 outbox，供社区索引、通知和异步资产登记消费。
- 日志统一记录 request、team/member、task、idempotency、release 和 schema 版本，不记录凭据。
- 将第三方许可证、依赖清单、静态文件哈希和 SBOM 纳入 release manifest。
- 只有当任务状态、配额和锁都已外置后，才评估多 worker、独立队列或对象存储。

## 3. 本地到生产的数据兼容策略

### 3.1 迁移原则

- 采用 expand-contract：先增加兼容表/列和双读逻辑，旧代码能够忽略新增结构；验证完成后再停止旧写。
- 不复制业务记录来“归属团队”，只通过稳定 ID 和关系字段增量映射。
- 不修改既有用户名、密码哈希、供应商父子 ID、平台账号 ID、资产 ID、草稿 ID 或媒体路径。
- 旧记录没有 team 字段时按原作者、账号和供应商关系推导；未来新个人用户不得自动并入 ACG。
- 任何用户名 canonical collision、固定团队 ID/name/slug 冲突、多 owner、成员已属于其他团队、账号/供应商已有冲突映射或孤儿关系都必须在 dry-run 中显式报错并阻断；不得用 `INSERT OR IGNORE` 后写 marker 的方式跳过。

### 3.2 ACG 固定映射

- 现有主管理员映射为 `ACG市场部` 唯一所有者，凭据不变。
- 其他管理员映射为团队管理员，既有创作者映射为团队成员。
- 既有供应商父子关系、平台账号及历史资源增量归入 ACG；供应商端继续是独立工作区。
- 个人用户和未来外部团队的数据、平台账号、草稿、任务、资产及 Blob 与 ACG 隔离。

完整团队迁移步骤继续以 `docs/ACG市场部生产团队迁移计划.md` 为执行基线。

## 4. 生产迁移与部署步骤

### 4.0 用户确认的唯一生产执行顺序

备份、恢复演练、依赖封板和用户授权是前置条件。进入迁移后只允许按以下门禁顺序前进，不得跨步或并行：

1. **v140 增量目标 release**：生产已受保护运行 `9e8aeb5`；从最终批准提交构建 `20260804-v140-delivery-media-publish-1` 不可变 release，仅放到 `/data/dumate-studio/releases/<id>`。新 release 继续通过已验收绝对路径读写现有持久根；不重做团队/资源/媒体全量迁移，不搬动约 15 GB 文件，不用 release 目录覆盖持久数据。当前唯一数据库变化是 expand-only `140005` compose claim 表。
2. **完整八步迁移与当前增量**：新副本完整顺序为 `137003`→`137004`→`139001`→`140001`→`140002`→`140003`→`140004`→`140005`，不得跳步或并行。`137004` 先 ACG preflight，`140002` 先 resource preflight，`140004` 先 media preflight。生产已完成前七步，本次只以 fresh v2 备份绑定精确 apply `140005` 两次，第二次必须零写；不得重跑前三个 data migration。
3. **每步 fresh backup binding**：每个 apply 前立即重新使用 SQLite backup API 生成 v2 manifest/闭合数据库副本并独立记录 manifest SHA-256。上一步已改变逻辑摘要，其备份绑定必须作废。
4. **副本双演练后才能写生产**：同环境副本上第二轮零新增/零重复，resource scope 100%，可开放媒体全部唯一归属，且权限/文件正负矩阵、完整恢复、离线依赖和 usage 门禁全部通过，才允许在冻结的生产库复制同一顺序。
5. **RO 验收与 RW 解锁分开**：只读 release 可在旧库上启动以核对路径、sidecar、画布和迁移状态，此时 `writeReady=false` 是预期。只有迁移、对账与安全验收后的 RW 启动预检返回 `writeReady=true` 才能解除写冻结；真实付费生成/发布仍需另行授权。

所有 apply 期间主服务、sidecar、后台任务和其他 writer 必须停止或由服务端冻结。只读 status/preflight 使用 `ACG_READ_ONLY=1`；只有当次 CLI 进程可临时设为 `0` 并带对应 ALLOW/版本/identity/backup hash，不改写外部环境文件。

### 阶段 A：部署前只读预检

在不触发应用初始化或状态 heal 的强制只读模式下，重新取得并记录：实际 commit 与缓存标识、systemd 与 worker 数、锁定依赖、Python/SQLite/FFmpeg 版本、有效环境加载来源、数据库 realpath 与生产身份、表结构、WAL 状态、`quick_check`、稳定 ID 集合摘要、各业务表计数、团队/供应商/平台账号关系、受保护目录文件数/字节数/hash、模型用量 spool/outbox 状态和画布 63 文件静态闭包标识。任何值缺失、路径落入 release 或数据库身份不符，都不能把版本标记为可切换。

### 阶段 B：一致性备份

1. 冻结写入并确认没有在途写任务。
2. 使用 Python SQLite backup API 生成一致性数据库副本并执行 `quick_check`、大小与 SHA-256 核验；不得因服务器缺少 `sqlite3` CLI 而退化为直接复制活动中的 `data.sqlite*`。只有经过预演证明一致的底层快照方案才可替代 backup API。
3. 使用 `deploy/runtime-snapshot.production-v120.plan.example.json` 的 `acg-production-complete-v1` profile 绑定环境配置、认证状态、systemd/Nginx、uploads、composed、canvas blobs、视频 runtime、BGM、模型缓存、`MODEL_USAGE_COMPLETION_SPOOL_DIR` 及现有代码/静态闭包；任一必保组件漏项 fail closed，spool 与 SQLite 必须属于同一恢复一致性点。计划中只有 `model-cache` 与 `nginx-site` 可显式安全解引用：模型缓存链接必须相对且最终留在组件根内，Nginx 目标必须留在 `/etc/nginx` 内；归档按真实字节验签并在隔离恢复中物化为普通文件，不得为迁就工具改写现网模型缓存。
4. 为受保护目录生成相对路径、文件数、总字节和 SHA-256 inventory；备份放在同步目录之外，并在进入下一阶段前完成一次隔离恢复演练。

### 阶段 C：同环境副本双演练

1. 从已通过恢复演练的生产备份建立隔离副本，使用与生产相同的有效环境加载方式、固定持久路径、锁定依赖、Python、SQLite、FFmpeg 和字体。
2. 新环境按 `137003`→`137004`→`139001`→`140001`→`140002`→`140003`→`140004`→`140005` 执行；当前 `9e8aeb5` 生产只执行 `140005`。每个 apply 前重新生成 v2 备份绑定，每个 data migration 先做只读 preflight。
3. 对新的原始副本重复整个顺序；第二轮必须零新增、零重复、零归属漂移，migration ledger/checksum 和 `quick_check` 一致。
4. 核对生产 `admin` 是 ACG 唯一 owner、其他既有管理员为团队管理员、既有创作者为团队成员、供应商和账号一对一绑定、无孤儿账号/资产、稳定 ID 集合不减少、owner/team/供应商关系摘要不漂移、凭据哈希不变、`quick_check=ok`。新增记录必须单独解释，不能用新增数量抵消记录丢失。
5. 核对媒体相对路径、文件大小和 hash inventory 不减少或异常变化。
6. 分别用目标 release 和兼容回滚 release 做登录、租户隔离、历史数据/媒体读取演练；原始 v120 只做历史基线比较，不作为迁移后可切换回滚版本。
7. 只读执行历史用量 `scan`，人工核对 observation manifest；仅在隔离目录数据库副本执行 `apply` 与 `reconcile-copy` 两次，第二次必须零写入，旧 usage event 原始 ID/member ID/824 与 1,186 行不变。任何无法证明的 token、日期或导演调用不进入恢复。
8. 在同规格磁盘暖库后连续 5 轮运行 64/128 路 receipt 压测：零异常、零重复授权；64 P99≤750ms、128 P99≤1s、单次≤1.25s、事件循环 P99 gap≤100ms，外部长锁期间零 provider call。

### 阶段 D：版本化发布

1. 从用户确认的本地提交创建干净 detached worktree。
2. 在干净源码中重建无限画布，核对闭包恰为 63 个文件且 manifest 的相对路径、大小和 SHA-256 全部匹配。
3. 使用锁定依赖预建目标 release 和兼容回滚 release 的独立环境，生成只包含代码和静态文件的 release 包；不得使用删除式同步，维护窗内不得联网安装依赖。
4. 部署到新的版本目录，保持旧 release、兼容回滚 release 与 release 外持久数据目录不动；再次核对有效环境不会回落到新 release 内的空路径。
5. 仅通过本文件的唯一 runbook 按七步顺序前进；在 RW 启动预检返回 `writeReady=true` 之前，写入口始终冻结。

### 阶段 E：开放写入前验收

- 服务：主服务、sidecar、单 worker 限制、release/schema 标识一致。
- 数据：业务计数、稳定 ID 集合和 owner/team/供应商关系摘要无异常漂移；新增记录单列解释；媒体相对路径、大小和 hash inventory 无异常减少；SQLite 检查通过。
- 角色：ACG owner/admin/member、个人、外部团队、供应商父/子、游客登录矩阵。
- 隔离：个人与外部团队不能读取 ACG 平台账号、资产、草稿、任务或 Blob。
- 链路：生产只读验收团队、供应商、发布清单、社区、收藏、历史资产与画布旧草稿；团队申请、写入/删除、配额结算和失败退款在隔离副本完成。
- 文件：历史图片可读、视频支持 Range、上传/成片/Blob 路径均可访问。

以上验收必须在强制只读模式完成，GET 不得触发 `_ensure_db()`、状态 heal 或任何隐式写入。目标 release 与兼容回滚 release 均通过后，才按 4.0 的最后一步开放写入。真实付费生成、真实发布或外部消息只在用户另行授权后执行。

## 5. 回滚方案

- **开放写入前失败**：停止目标 release，优先切换到已验证的兼容回滚 release。只有维护窗始终保持全部写入口冻结、能够证明快照后没有任何业务或 runtime 写入，并已验证数据库与媒体快照属于同一一致性点时，才允许整套恢复到生产 v120 快照；否则保留迁移后的数据库并执行前向数据修复。
- **开放写入后失败**：再次冻结写入并先保存事故后数据库和媒体；只允许回滚到理解新 schema、租户隔离、个人/团队账号与配额语义的兼容回滚 release，数据通过前向修复，禁止切回原始 v120 代码，也禁止用旧库覆盖新业务。
- 新迁移默认只扩展，不立即删除旧列/旧表；旧代码必须能忽略新增结构。
- 回滚后重新执行 readiness、SQLite、计数、角色、供应商和租户隔离核验。
- 兼容回滚 release、目标 release 与数据快照必须使用同一 release manifest/迁移兼容矩阵登记；“进程能启动”或“旧版能 SELECT”不等于可安全回滚。
