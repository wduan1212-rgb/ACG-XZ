# 本地代码架构优化与服务器迁移部署方案

记录日期：2026-08-03

状态：**v137 已在本地提交 Phase 0/1 部署安全层（代码 `52e3d72`）：环境先于 store 解析、生产普通启动 validate-only、`137003` schema 账本、`137004` ACG 显式预检/应用与冻结 scope、主服务/sidecar 强制只读、受保护的 `/api/ready`、release/ESM/画布 manifest 校验、SQLite backup API 和 release 外持久路径门禁。这些仍未在生产副本或生产执行；租户资源归属与媒体 owner registry 未收口，因此仍禁止开放生产写入。本轮未推送、未部署；生产事实沿用前段固定只读盘点，最终收口阶段没有发起新的远端命令，也未修改服务器、生产数据库、生产文件及私密配置。**

本方案以当前 v137 共享工作区源码和 2026-08-03 已取得的生产只读快照为依据。快照确认生产仍是 v120 缓存基线，活动 `current` 为实体目录，SQLite 与约 15 GB 受保护媒体仍和代码同目录，生产仅有 12 张业务表。详细事实与 ACG 数据归属门禁记录在 `docs/ACG市场部生产团队迁移计划.md`。这些计数会随业务变化，获准部署的维护窗前仍须重新只读核对；`/api/health` 只证明存活，只有完整 readiness、副本迁移和权限/媒体矩阵才能证明可开放写入。

## 1. 当前架构判断

### 1.1 应保留的边界

- 主平台继续作为唯一公网入口，负责身份、租户、配额、资产、社区、供应商和任务登记。
- 视频工坊继续作为仅监听回环地址的 sidecar；不要把其依赖和媒体流水线合并回主进程。
- 静态视频继续走图片分镜、可选 TTS、字幕/BGM 与本地合成链路，不进入 Seedance；分镜按语义及存在的口播自然拆分，只要求整体时长大致合理，不建立精确时长约束，也不强制用户提供或生成口播。
- 无限画布继续保持“React 源码 + 审计后的静态闭包 + 同源 iframe”边界；服务器运行只读取静态闭包，源码用于重建和审计。
- SQLite、uploads、composed、canvas blobs、视频工坊 runtime、模型缓存、环境变量和认证状态均属于持久数据或私密配置，不进入代码发布包。

### 1.2 当前主要风险

| 风险 | 当前证据 | 影响 |
| --- | --- | --- |
| 主服务与存储层仍过度集中 | 鉴权、团队、供应商、计费、媒体和迁移仍集中在 `server/main.py` / `server/store.py` | 后续应按域机械拆分，不在迁移 release 同时改 API 或数据形状 |
| 生产 schema 跨度过大 | 生产 v120 只读快照为 12 张业务表且 `user_version=0`；v137 已将结构与 ACG 数据分为 `137003` / `137004` | 代码实现不等于生产可执行，必须在同环境副本连续演练并核对账本/checksum |
| 租户鉴权仍有跨域缺口 | 已实证通用 `role=admin` 可跨租户读写/删除部分 collection；通用 `resource_scopes` 覆盖率尚未达 100% | 不得因 ACG 迁移完成就开放写入；必须改为 deny-by-default 并通过 A/B 负向矩阵 |
| 媒体缺少 owner registry | `uploads` / `composed` 仍使用直接 URL，没有完整 owner/team 归属账本 | 直接加 bearer 鉴权会破坏现有 `<img>/<video>` 读取；必须先建 registry/scope 与兼容读策略 |
| 供应商边界需要生产映射验证 | 本地已收口唯一 team mapping、team account 和 child binding 的 fail-closed 切片 | 生产必须先完成 `137004` 映射，再用团队 A/B 和供应商父/子矩阵证明无越权 |
| 关键写失败不可见 | 普通集合写仍存在吞掉失败的兼容通道 | 画布、资产或计费状态可能在前端显示成功而服务器未持久化 |
| 任务状态偏进程内 | 视频闸门依赖单进程内存状态 | 多 worker 或重启后并发限制和终态恢复不可靠 |
| 静态闭包漂移 | 本地 manifest 指定 61 文件/1,761,292 bytes，生产 v120 活动 vendor 目录为 128 文件/约 4.0 MB | 已有 verifier 与 readiness 门禁，但生产必须用 manifest 构造新闭包，不得覆盖或复用旧目录 |
| 代码与持久数据同目录 | 生产 `current` 不是版本 symlink，SQLite、uploads、composed、canvas blobs、视频 runtime 与环境文件都在活动目录内 | 未先完成独立路径迁移和恢复演练时，整目录覆盖、删除式同步或假设原子切换都会危及数据 |
| 部署说明曾分叉 | `deploy/README.md` 已收敛为 v137 生产只读契约，但历史聊天和旧 release 仍可能保留删除式同步示例 | 部署只能读取批准 commit 内的当前四份权威文档，不能复用历史命令 |

## 2. 目标架构

目标不是一次性重写，而是在保持现有 API、数据库和媒体 URL 可读的前提下逐步拆分。

```text
Browser / Desktop Client
        |
        v
Main API (8787, single public entry)
  ├─ routers: auth / teams / supplier / assets / community / canvas / video
  ├─ policies: TenantContext / AuthPolicy
  ├─ services: Billing / AssetRegistry / Community / CanvasCheckpoint / Job
  ├─ repositories: users / teams / documents / tasks / media
  ├─ migrations: numbered, checksum, forward-only
  └─ readiness: release + schema + data paths + sidecar + vendor manifest
        |
        ├─ SQLite (current transactional source of truth)
        ├─ protected media directories / future object storage
        └─ Video Workshop sidecar (8765, loopback only)

Infinite Canvas
  source -> reproducible build -> manifest -> audited vendor closure -> iframe
```

### 2.1 v137 已实现的 Phase 0/1 安全层

- `server.config` 在 store 之前加载外部环境；生产强制 `validate` 启动，要求 SQLite 和受保护目录位于显式持久根目录且在 release 之外，缺失或身份不符时 fail closed。
- `137003` 是 expand-only schema 迁移，`137004` 是 ACG 数据迁移；两者均进入 `schema_migrations` checksum/status 账本，只能通过独立 CLI 和专用授权执行。`137004` 先 dry-run，再冻结本次 member/supplier/account/identity scope，不隐式全表收编。
- 未提交中间构建曾在本机写入旧 `137001` checksum；最终源码没有覆盖或删除这条账本，而是使用新的 `137003/137004`。这条本地证据再次证明 migration version 一经写入即不可复用，生产与副本不得执行已退役的 `137001/137002`。
- 主服务和视频 sidecar 都有服务端强制只读契约；主库使用 `mode=ro/query_only`，写路由被拒绝，视频项目 GET 不再触发恢复、自动续跑或计费同步。
- 受保护的 `/api/ready` 综合检查 release、SQLite `quick_check`、`137003`/`137004` 及 dirty/checksum、固定持久路径、视频 sidecar `ready/readOnly/writePolicy`、内部团队漂移和无限画布 manifest；`/api/health` 仍只表示存活。
- release verifier 检查原生 ESM 图的单一物理模块/单一 URL 身份，并对画布 61 文件的路径、大小、SHA-256 和无额外文件做独立验签。
- 一致备份脚本使用 Python SQLite backup API，备份后校验 `quick_check`、大小和 SHA-256，不存在活动库原始 `cp` 兜底；启动脚本在停服/备份前执行 release 契约门禁。

上述是“已实现的本地安全机制”，不是“已完成生产迁移”。只有在同环境生产副本完成双演练、备份恢复验证和只读浏览器验收后，才能进入生产维护窗。

### 2.2 仍然存在的 P0 部署阻断

1. **统一租户策略未完成**：通用 collection 仍存在 `role=admin` 跨租户读写/删除通道；必须建立完整 `resource_scopes`，将 collection、production/job、账号、资产、草稿、analytics、社区、配额、画布 Blob 和视频项目收口为 deny-by-default。
2. **媒体归属未完成**：`uploads` / `composed` 必须建立 owner/team registry 和兼容的媒体读取授权，覆盖 Range、缓存和历史直接 URL；未达到 coverage=100%、orphan=0、conflict=0 前不得开放写入。
3. **供应商切片尚需生产映射演练**：本地 fail-closed 修复不能代替 `137004` 对旧供应商/账号的映射；必须用外部团队 A/B 和父/子供应商进行正负矩阵。
4. **发布环境与回滚未封板**：主服务/sidecar 依赖锁、离线环境和兼容演进库的回滚 release 仍须形成。一旦执行 `137003` 或 `137004`，原始 v120 代码不能读取演进库，也不能作为代码回滚目标。
5. **迁移尚未原子绑定已验证备份**：SQLite backup helper 已能生成一致副本、`quick_check`、size/SHA-256 并 fsync，但 `137003/137004 apply` 尚未强制要求 manifest v2，也没有在同一 `BEGIN IMMEDIATE` 内比对当前目标库 identity/逻辑摘要与备份点。生产迁移前必须做到任一不匹配零写退出，不能用人工口头确认代替代码门禁。
6. **生产证据尚缺**：必须在部署日重取实时基线，完成 SQLite/媒体一致备份恢复、副本连续迁移两次、凭据不变验证和上述权限/媒体矩阵。

### 2.3 P1：降低耦合

- 将 `server/main.py` 拆为 `api/auth.py`、`teams.py`、`supplier.py`、`assets.py`、`community.py`、`canvas.py`、`video.py`；旧路径先作为兼容适配器，不同时改调用方和存储结构。
- 将 `server/store.py` 拆为 repositories 与 services。路由只负责参数、鉴权和响应；事务由服务层拥有。
- 建立统一 `BillingService` 与不可变结算流水，图片、TTS、音色、动态/静态视频都只通过同一 reserve→settle/release 协议。
- 建立 `AssetRegistry`，记录 owner/team、对象 hash、MIME、大小、来源任务和状态；现有文件路径与 URL 继续双读，逐步回填，不做一次性搬库。
- 视频任务改为持久任务表、lease、heartbeat 和明确终态。完成前保持单 worker，避免多个 worker 绕开进程内并发门。
- iframe `postMessage` 增加 `protocolVersion`、capability handshake 和向后兼容分支。

### 2.4 P2：长期演进

- 通用 documents JSON 按域使用 shadow write、dual read、回填校验逐步迁入显式表；确认一致后才切读，禁止一次性大迁移。
- 增加事务 outbox，供社区索引、通知和异步资产登记消费。
- 日志统一记录 request、team/member、task、idempotency、release 和 schema 版本，不记录凭据。
- 将第三方许可证、依赖清单、静态文件哈希和 SBOM 纳入 release manifest。
- 只有当任务状态、配额和锁都已外置后，才评估多 worker、独立队列或对象存储。

## 3. 本地到生产的数据兼容策略

### 3.1 迁移原则

- 采用 expand-contract：先增加兼容表/列和双读逻辑，旧代码能够忽略新增结构；验证完成后再停止旧写。
- 不复制业务记录来“归属团队”，只通过稳定 ID 和关系字段增量映射。
- 不修改既有用户名、密码哈希、供应商父子 ID、平台账号 ID、资产 ID、草稿 ID 或媒体路径。
- 旧记录没有 team 字段时按原作者、账号和供应商关系推导；未来新个人用户不得自动并入 ACG。
- 任何用户名 canonical collision、固定团队 ID/name/slug 冲突、多 owner、成员已属于其他团队、账号/供应商已有冲突映射或孤儿关系都必须在 dry-run 中显式报错并阻断；不得用 `INSERT OR IGNORE` 后写 marker 的方式跳过。

### 3.2 ACG 固定映射

- 现有主管理员映射为 `ACG市场部` 唯一所有者，凭据不变。
- 其他管理员映射为团队管理员，既有创作者映射为团队成员。
- 既有供应商父子关系、平台账号及历史资源增量归入 ACG；供应商端继续是独立工作区。
- 个人用户和未来外部团队的数据、平台账号、草稿、任务、资产及 Blob 与 ACG 隔离。

完整团队迁移步骤继续以 `docs/ACG市场部生产团队迁移计划.md` 为执行基线。

## 4. 生产迁移与部署步骤

### 4.0 用户确认的唯一生产执行顺序

备份、恢复演练、依赖封板和用户授权是前置条件。进入迁移后只允许按以下门禁顺序前进，不得跨步或并行：

1. **v137 只读兼容 release**：从批准提交构建只含代码/静态文件的不可变 release，验证 ESM 图、sidecar 契约、画布 manifest 和 release 外持久路径。主服务与 sidecar 全程保持只读；迁移未完成前 `/api/ready` 拒绝属于预期门禁。
2. **生产副本 schema**：从一致备份恢复同环境副本，单实例执行 `137003`，核对 checksum/status、`quick_check`、稳定 ID 与计数；第二次必须零结构变化。
3. **ACG data**：在同一副本先执行 `137004` dry-run，冲突为零后才 apply；dry-run 不持久化 scope，apply 会在同一写事务内重新预检并冻结当次 scope。核对唯一 owner、成员/供应商/账号映射及凭据不变，第二次必须零新增、零重复、零归属漂移。
4. **权限/媒体 scope 完整**：只有通用 `resource_scopes` 和 uploads/composed owner registry 达到 coverage=100%、orphan=0、conflict=0，且 ACG/个人/外部团队 A/B/供应商父子/游客的读写删与文件负向矩阵全部通过，才允许将 `137003` 和 `137004` 按相同顺序用于写入冻结的生产库。
5. **开放写入**：生产库仍以只读方式启动，通过 `/api/ready`、数据/媒体 inventory、只读浏览器验收和兼容回滚 release 验证后，才能解除写入冻结。真实付费生成、真实发布或外部消息仍需用户另行授权。

步骤 2/3 的 apply 期间，主服务、sidecar、后台任务和其他 writer 必须保持停止或服务端冻结；只读 status/preflight 继续使用 `ACG_READ_ONLY=1`。只有单独迁移 CLI 进程可临时覆盖 `ACG_READ_ONLY=0`，并同时提供对应专用 ALLOW、版本和数据库 identity 确认；apply 结束后先恢复只读再启动服务。禁止把生产外部环境文件永久改为可写。

### 阶段 A：部署前只读预检

在不触发应用初始化或状态 heal 的强制只读模式下，重新取得并记录：实际 commit 与缓存标识、systemd 与 worker 数、锁定依赖、Python/SQLite/FFmpeg 版本、有效环境加载来源、数据库 realpath 与生产身份、表结构、WAL 状态、`quick_check`、稳定 ID 集合摘要、各业务表计数、团队/供应商/平台账号关系、受保护目录文件数/字节数/hash 和画布 61 文件静态闭包标识。任何值缺失、路径落入 release 或数据库身份不符，都不能把版本标记为可切换。

### 阶段 B：一致性备份

1. 冻结写入并确认没有在途写任务。
2. 使用 Python SQLite backup API 生成一致性数据库副本并执行 `quick_check`、大小与 SHA-256 核验；不得因服务器缺少 `sqlite3` CLI 而退化为直接复制活动中的 `data.sqlite*`。只有经过预演证明一致的底层快照方案才可替代 backup API。
3. 独立保存环境配置、认证状态、systemd、uploads、composed、canvas blobs、视频 runtime、BGM、模型缓存及现有代码/静态闭包。
4. 为受保护目录生成相对路径、文件数、总字节和 SHA-256 inventory；备份放在同步目录之外，并在进入下一阶段前完成一次隔离恢复演练。

### 阶段 C：同环境副本双演练

1. 从已通过恢复演练的生产备份建立隔离副本，使用与生产相同的有效环境加载方式、固定持久路径、锁定依赖、Python、SQLite、FFmpeg 和字体。
2. 先连续执行 `137003` 两次，第二次必须零结构变化，再核对账本/checksum 和 `quick_check`。
3. 再执行 `137004` dry-run/apply，记录冻结 scope 和脱敏摘要；第二次必须零新增、零重复、零归属漂移。
4. 核对生产 `admin` 是 ACG 唯一 owner、其他既有管理员为团队管理员、既有创作者为团队成员、供应商和账号一对一绑定、无孤儿账号/资产、稳定 ID 集合不减少、owner/team/供应商关系摘要不漂移、凭据哈希不变、`quick_check=ok`。新增记录必须单独解释，不能用新增数量抵消记录丢失。
5. 核对媒体相对路径、文件大小和 hash inventory 不减少或异常变化。
6. 分别用目标 release 和兼容回滚 release 做登录、租户隔离、历史数据/媒体读取演练；原始 v120 只做历史基线比较，不作为迁移后可切换回滚版本。

### 阶段 D：版本化发布

1. 从用户确认的本地提交创建干净 detached worktree。
2. 在干净源码中重建无限画布，核对闭包恰为 61 个文件且 manifest 的相对路径、大小和 SHA-256 全部匹配。
3. 使用锁定依赖预建目标 release 和兼容回滚 release 的独立环境，生成只包含代码和静态文件的 release 包；不得使用删除式同步，维护窗内不得联网安装依赖。
4. 部署到新的版本目录，保持旧 release、兼容回滚 release 与 release 外持久数据目录不动；再次核对有效环境不会回落到新 release 内的空路径。
5. 仅通过本文件的唯一 runbook，按“只读 release→`137003`→`137004`→权限/媒体 scope→readiness”顺序前进；在最后验收前写入口始终冻结。

### 阶段 E：开放写入前验收

- 服务：主服务、sidecar、单 worker 限制、release/schema 标识一致。
- 数据：业务计数、稳定 ID 集合和 owner/team/供应商关系摘要无异常漂移；新增记录单列解释；媒体相对路径、大小和 hash inventory 无异常减少；SQLite 检查通过。
- 角色：ACG owner/admin/member、个人、外部团队、供应商父/子、游客登录矩阵。
- 隔离：个人与外部团队不能读取 ACG 平台账号、资产、草稿、任务或 Blob。
- 链路：生产只读验收团队、供应商、发布清单、社区、收藏、历史资产与画布旧草稿；团队申请、写入/删除、配额结算和失败退款在隔离副本完成。
- 文件：历史图片可读、视频支持 Range、上传/成片/Blob 路径均可访问。

以上验收必须在强制只读模式完成，GET 不得触发 `_ensure_db()`、状态 heal 或任何隐式写入。目标 release 与兼容回滚 release 均通过后，才按 4.0 的最后一步开放写入。真实付费生成、真实发布或外部消息只在用户另行授权后执行。

## 5. 回滚方案

- **开放写入前失败**：停止目标 release，优先切换到已验证的兼容回滚 release。只有维护窗始终保持全部写入口冻结、能够证明快照后没有任何业务或 runtime 写入，并已验证数据库与媒体快照属于同一一致性点时，才允许整套恢复到生产 v120 快照；否则保留迁移后的数据库并执行前向数据修复。
- **开放写入后失败**：再次冻结写入并先保存事故后数据库和媒体；只允许回滚到理解新 schema、租户隔离、个人/团队账号与配额语义的兼容回滚 release，数据通过前向修复，禁止切回原始 v120 代码，也禁止用旧库覆盖新业务。
- 新迁移默认只扩展，不立即删除旧列/旧表；旧代码必须能忽略新增结构。
- 回滚后重新执行 readiness、SQLite、计数、角色、供应商和租户隔离核验。
- 兼容回滚 release、目标 release 与数据快照必须使用同一 release manifest/迁移兼容矩阵登记；“进程能启动”或“旧版能 SELECT”不等于可安全回滚。
