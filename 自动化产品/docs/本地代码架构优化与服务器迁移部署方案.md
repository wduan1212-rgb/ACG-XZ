# 本地代码架构优化与服务器迁移部署方案

记录日期：2026-08-03

状态：**v136 已完成本地代码与自动验证收口，功能提交为 `03882da`；历史 `88a0460` 是 61 文件画布静态闭包来源，`61346a4` 是此前功能快照，均不是可部署 release。v136 新增社区 identity schema，但正式迁移、强制只读模式、租户门禁、可靠备份恢复、锁定依赖及兼容回滚 release 仍未完成，因此明确禁止部署、禁止执行生产迁移。未推送生产发布，未连接或修改生产数据库、服务器文件。**

本方案以当前本地 v136 功能提交 `03882da`、历史画布闭包 `88a0460` 和最近一次部署记录中的生产 v120 基线为依据。本轮只检查本地双服务健康，没有连接生产；生产内部实况仍需在获准部署的维护窗前重新只读核对。因此，以下方案区分“已由本地代码确认的事实”和“部署前必须重新取得的生产事实”，不把本地 `/api/health` 等同于上线兼容，也不把任何当前提交描述为可部署版本。

## 1. 当前架构判断

### 1.1 应保留的边界

- 主平台继续作为唯一公网入口，负责身份、租户、配额、资产、社区、供应商和任务登记。
- 视频工坊继续作为仅监听回环地址的 sidecar；不要把其依赖和媒体流水线合并回主进程。
- 静态视频继续走图片分镜、可选 TTS、字幕/BGM 与本地合成链路，不进入 Seedance；分镜按语义及存在的口播自然拆分，只要求整体时长大致合理，不建立精确时长约束，也不强制用户提供或生成口播。
- 无限画布继续保持“React 源码 + 审计后的静态闭包 + 同源 iframe”边界；服务器运行只读取静态闭包，源码用于重建和审计。
- SQLite、uploads、composed、canvas blobs、视频工坊 runtime、模型缓存、环境变量和认证状态均属于持久数据或私密配置，不进入代码发布包。

### 1.2 当前主要风险

| 风险 | 当前证据 | 影响 |
| --- | --- | --- |
| 主服务过度集中 | `server/main.py` 约 9,070 行、约 138 个路由 | 鉴权、团队、供应商、计费和媒体改动相互影响，回归半径过大 |
| 存储层过度集中 | `server/store.py` 约 9,274 行 | schema、隐式迁移、租户投影、配额和社区共用一个模块，难以审计事务边界 |
| 启动即迁移 | `_ensure_db()` 仍会建表、补列、修角色和修团队归属 | 生产启动本身会改数据，无法做到迁移预演、checksum 和单独回滚 |
| 社区 schema 未进入账本 | v136 新增 `community_post_identities` 和作者+identity 唯一约束，当前仍由 `_ensure_db()` 建立 | 直接启动目标代码会在生产库隐式写 schema，无法先 dry-run、审计或独立回滚 |
| 缺少 readiness | 只有健康接口，没有迁移、数据库、目录、sidecar 与静态闭包门禁 | 服务存活可能被误报为数据与版本兼容 |
| 关键写失败不可见 | 普通集合写仍存在吞掉失败的兼容通道 | 画布、资产或计费状态可能在前端显示成功而服务器未持久化 |
| 任务状态偏进程内 | 视频闸门依赖单进程内存状态 | 多 worker 或重启后并发限制和终态恢复不可靠 |
| 静态闭包漂移 | 本地已把 `vendor/infinite-canvas` 收口为 manifest 指定的 61 文件，但服务器尚未取得同一 closure/hash 基线 | 发布包只能携带 manifest 内文件；切换前必须由 `/api/ready` 核对闭包 hash，不能复用历史混杂目录 |
| 部署说明分叉 | 旧部署 README 仍有示例目录和删除式同步写法 | 容易把历史示例误当成当前生产事实 |

## 2. 目标架构

目标不是一次性重写，而是在保持现有 API、数据库和媒体 URL 可读的前提下逐步拆分。

```text
Browser / Desktop Client
        |
        v
Main API (8787, single public entry)
  ├─ routers: auth / teams / supplier / assets / community / canvas / video
  ├─ policies: TenantContext / AuthPolicy
  ├─ services: Billing / AssetRegistry / Community / CanvasCheckpoint / Job
  ├─ repositories: users / teams / documents / tasks / media
  ├─ migrations: numbered, checksum, forward-only
  └─ readiness: release + schema + data paths + sidecar + vendor manifest
        |
        ├─ SQLite (current transactional source of truth)
        ├─ protected media directories / future object storage
        └─ Video Workshop sidecar (8765, loopback only)

Infinite Canvas
  source -> reproducible build -> manifest -> audited vendor closure -> iframe
```

### 2.1 P0：部署前必须完成

以下任一项未完成，v136 都保持“本地收口、禁止部署”。

1. **环境加载与生产数据身份 fail-closed**
   - 必须在导入 `server.store`、解析 `DATA_DB` / `UPLOAD_DIR` 等路径之前加载受保护环境；部署脚本不得用 release 目录内默认值覆盖服务器环境文件。
   - `.env*`、SQLite、uploads、composed、canvas blobs、视频 runtime、模型缓存和认证状态必须位于 release 目录之外的固定绝对路径，并由 systemd 或单一受保护环境文件显式注入。
   - 升级模式要求数据库已存在、是普通文件且可解析到批准的持久目录；同时核对稳定 ID 摘要、关键集合基线和生产身份标记。路径缺失、落入 release、身份不符或读到空库时必须拒绝启动，禁止自动建库或播种后继续。

2. **正式迁移账本与强制只读模式**
   - 新增 `schema_migrations(version, name, checksum, app_version, started_at, finished_at, status, summary)`。
   - 将 `_ensure_db()` 内的结构变化和 ACG 数据归属修复拆成编号、前向、幂等迁移。
   - 应用普通启动只检查迁移状态；存在 pending、running、failed、dirty 或 checksum 不一致时必须 fail-closed。生产迁移只允许由独立命令在单实例、冻结写入状态下执行，业务请求不能隐式触发建表、补列、凭据规范化、角色修复或团队归属变化。
   - 每个迁移在生产副本连续执行两次，第二次必须零重复、零角色漂移。
   - 增加受保护的只读运行模式：SQLite 以 `mode=ro` 打开，禁用 `_ensure_db()`、运行态 heal、配额初始化及所有写路由；部署前盘点和开放写入前浏览器验收必须在此模式完成，GET 请求不得产生数据库写入。

3. **TenantContext / AuthPolicy 统一租户门禁**
   - 所有 collection、production/job、账号、资产、草稿、analytics、社区、配额、文件、画布 Blob 和视频 sidecar 项目都必须通过同一 `TenantContext + AuthPolicy` 判定，默认拒绝，不能再以 `role == admin` 代表跨租户全局读写。
   - 补齐角色×团队×资源×动作矩阵，至少覆盖 ACG owner/admin/member、个人用户、两个相互独立的外部团队 owner/admin/member、供应商父/子账号和游客的 GET/PUT/DELETE/文件读取。
   - 当前内部管理员读取其他租户未发布 production/jobs、通用 admin 写删和文件覆盖等缺口修复并形成负向回归前，禁止部署。

4. **受保护的 `/api/ready`**
   - 返回 `release_id`、主入口/共享模块/sidecar 缓存标识、schema 版本、pending/dirty 数和有效数据身份摘要。
   - 检查 SQLite `quick_check`、固定持久路径、单 worker、sidecar ready、无限画布 61 文件 manifest hash；任何不一致都返回非 2xx。
   - `/api/health` 只表示进程存活，不再作为部署门禁。

5. **关键写入必须有确认终态**
   - 画布 Blob→草稿 checkpoint、资产登记、社区分享、配额 reserve/settle/release 禁止使用静默吞错写入。
   - 每次关键写携带 request ID、idempotency key、revision 和明确的成功/失败终态。
   - 失败允许重试，但不得重复扣点或重复创建业务记录。

6. **可靠一致性备份与恢复演练**
   - 冻结全部写入口并确认没有业务、后台任务或 sidecar writer 后，使用 Python SQLite backup API 生成一致副本；不得在缺少 `sqlite3` CLI 时退化为未经验证的 `cp data.sqlite*`。
   - 数据库副本必须通过 `quick_check`、大小和 SHA-256 核验；uploads、composed、canvas blobs、视频 runtime、BGM、环境、认证状态、systemd 和旧代码/静态闭包必须形成位于同步目录之外的快照或相对路径+大小+SHA-256 inventory。
   - 生产切换前必须在隔离位置完成至少一次数据库与受保护媒体恢复演练，并重新核对稳定 ID、关系摘要和文件 hash；只有“备份存在”而没有恢复验证不算通过。

7. **锁定依赖和不可变运行环境**
   - 主服务与 sidecar 的 Python 依赖必须解析为锁文件和 wheel/hash 清单，记录 Python、SQLite、FFmpeg、字体与关键二进制版本。
   - 构建、迁移、启动严格分离；维护窗内和 systemd 重启时禁止 `pip install`、升级 pip 或下载依赖。目标 release 与兼容回滚 release 分别保留自己的已验证环境。

8. **锁定并门禁无限画布 61 文件静态闭包**
   - 从已提交源码的干净临时检出重建无限画布。
   - 发布闭包必须恰好包含 `61` 个文件；manifest 对每个文件记录唯一相对路径、大小和 SHA-256，并验证无缺失、无额外文件、无路径穿越，入口引用的构建 ID 与闭包一致。
   - 只把 `88a0460` manifest 中的 61 个文件作为发布闭包；生产切换前必须核对文件数、总字节数和每文件 SHA-256，不得混入历史哈希文件。
   - 本地闭包已随 `88a0460` 精确提交；生产不得复用服务器历史目录，必须从 release manifest 构造并验 hash。

9. **发布清单、数据排除与兼容回滚 release**
   - 每个 release 绑定来源 commit、迁移版本、依赖锁、缓存身份集及 61 文件画布 manifest。v136 当前身份集是主平台/视频工坊 `20260803-v136-community-static-1` 与供应商共享视图 `20260803-v136-supplier-shared-1`；每个模块只能出现一个批准的 canonical URL，不能要求供应商标识与主标识相同。
   - 永久排除 `.env*`、认证缓存、SQLite/WAL/SHM、uploads、composed、canvas blobs、runtime、模型缓存、备份、日志、虚拟环境和本地素材。
   - 在生产迁移前生成并验证一个理解新 schema、保留新租户隔离与新账号/配额语义的兼容回滚 release；迁移并开放新写入后，原始生产 v120 只能作为历史基线，不能直接作为代码回滚目标。

10. **唯一权威 runbook**
   - 本文件第 4 节是 v136 生产迁移的唯一权威顺序；执行前必须绑定用户批准的目标 commit、release manifest、维护窗口、实时生产基线和回滚点。
   - `deploy/README.md`、`deploy/start_server.sh`、Docker 示例和旧的“原地 restart + health”流程仅作通用/本地参考，不得用于 v136 生产迁移；不得混用 `/opt/...` 示例、`/data/dumate-studio/current` 实况或多套启动方式。
   - 未形成并批准单一版本化 runbook、或执行人与记录无法逐项勾选 P0 时，禁止部署。

### 2.2 P1：降低耦合

- 将 `server/main.py` 拆为 `api/auth.py`、`teams.py`、`supplier.py`、`assets.py`、`community.py`、`canvas.py`、`video.py`；旧路径先作为兼容适配器，不同时改调用方和存储结构。
- 将 `server/store.py` 拆为 repositories 与 services。路由只负责参数、鉴权和响应；事务由服务层拥有。
- 建立统一 `BillingService` 与不可变结算流水，图片、TTS、音色、动态/静态视频都只通过同一 reserve→settle/release 协议。
- 建立 `AssetRegistry`，记录 owner/team、对象 hash、MIME、大小、来源任务和状态；现有文件路径与 URL 继续双读，逐步回填，不做一次性搬库。
- 视频任务改为持久任务表、lease、heartbeat 和明确终态。完成前保持单 worker，避免多个 worker 绕开进程内并发门。
- iframe `postMessage` 增加 `protocolVersion`、capability handshake 和向后兼容分支。

### 2.3 P2：长期演进

- 通用 documents JSON 按域使用 shadow write、dual read、回填校验逐步迁入显式表；确认一致后才切读，禁止一次性大迁移。
- 增加事务 outbox，供社区索引、通知和异步资产登记消费。
- 日志统一记录 request、team/member、task、idempotency、release 和 schema 版本，不记录凭据。
- 将第三方许可证、依赖清单、静态文件哈希和 SBOM 纳入 release manifest。
- 只有当任务状态、配额和锁都已外置后，才评估多 worker、独立队列或对象存储。

## 3. 本地到生产的数据兼容策略

### 3.1 迁移原则

- 采用 expand-contract：先增加兼容表/列和双读逻辑，旧代码能够忽略新增结构；验证完成后再停止旧写。
- 不复制业务记录来“归属团队”，只通过稳定 ID 和关系字段增量映射。
- 不修改既有用户名、密码哈希、供应商父子 ID、平台账号 ID、资产 ID、草稿 ID 或媒体路径。
- 旧记录没有 team 字段时按原作者、账号和供应商关系推导；未来新个人用户不得自动并入 ACG。
- 任何用户名 canonical collision、固定团队 ID/name/slug 冲突、多 owner、成员已属于其他团队、账号/供应商已有冲突映射或孤儿关系都必须在 dry-run 中显式报错并阻断；不得用 `INSERT OR IGNORE` 后写 marker 的方式跳过。

### 3.2 ACG 固定映射

- 现有主管理员映射为 `ACG市场部` 唯一所有者，凭据不变。
- 其他管理员映射为团队管理员，既有创作者映射为团队成员。
- 既有供应商父子关系、平台账号及历史资源增量归入 ACG；供应商端继续是独立工作区。
- 个人用户和未来外部团队的数据、平台账号、草稿、任务、资产及 Blob 与 ACG 隔离。

完整团队迁移步骤继续以 `docs/ACG市场部生产团队迁移计划.md` 为执行基线。

## 4. 生产迁移与部署步骤

### 4.0 用户确认的唯一生产执行顺序

本次迁移只允许按以下顺序执行，不得跨步、并行或用旧部署脚本替代：

1. **冻结写入并完整备份**：冻结主平台、后台任务和 sidecar 的全部写入口，确认无在途 writer，完成数据库、媒体、环境、认证状态、systemd、旧代码/静态闭包的一致备份及恢复演练。
2. **生产副本同环境连续迁移两次**：从已验证备份建立隔离副本，使用生产相同的有效环境形状、固定持久路径、Python/SQLite/FFmpeg/字体和锁定依赖；第一次执行正式迁移，第二次必须零新增、零重复、零角色漂移。
3. **保留凭据**：迁移前后逐一比较用户名、登录身份和凭据哈希，任何差异立即阻断；不得打印哈希，也不得以默认配置覆盖生产凭据。
4. **完成 ACG 固定映射**：生产 `admin` 成为 `ACG市场部` 唯一所有者，其他既有管理员成为团队管理员，既有创作者成为团队成员；既有供应商父子关系、平台账号及其历史资源按稳定关系增量归入 ACG，不复制业务记录、不改变稳定 ID 或媒体路径。
5. **核验数据、隔离与登录矩阵**：稳定 ID、业务计数、owner/team/供应商摘要、删除墓碑、媒体 inventory 不异常减少；ACG、个人、外部团队 A/B、供应商父/子和游客的登录、读取、写入、删除、文件/Blob 隔离矩阵全部通过。
6. **开放写入**：只有目标 release、兼容回滚 release、readiness 和只读浏览器验收全部通过后，才解除写入冻结；真实付费生成、真实发布或外部消息仍需用户另行授权。

### 阶段 A：部署前只读预检

在不触发应用初始化或状态 heal 的强制只读模式下，重新取得并记录：实际 commit 与缓存标识、systemd 与 worker 数、锁定依赖、Python/SQLite/FFmpeg 版本、有效环境加载来源、数据库 realpath 与生产身份、表结构、WAL 状态、`quick_check`、稳定 ID 集合摘要、各业务表计数、团队/供应商/平台账号关系、受保护目录文件数/字节数/hash 和画布 61 文件静态闭包标识。任何值缺失、路径落入 release 或数据库身份不符，都不能把版本标记为可切换。

### 阶段 B：一致性备份

1. 冻结写入并确认没有在途写任务。
2. 使用 Python SQLite backup API 生成一致性数据库副本并执行 `quick_check`、大小与 SHA-256 核验；不得因服务器缺少 `sqlite3` CLI 而退化为直接复制活动中的 `data.sqlite*`。只有经过预演证明一致的底层快照方案才可替代 backup API。
3. 独立保存环境配置、认证状态、systemd、uploads、composed、canvas blobs、视频 runtime、BGM、模型缓存及现有代码/静态闭包。
4. 为受保护目录生成相对路径、文件数、总字节和 SHA-256 inventory；备份放在同步目录之外，并在进入下一阶段前完成一次隔离恢复演练。

### 阶段 C：同环境副本双演练

1. 从已通过恢复演练的生产备份建立隔离副本，使用与生产相同的有效环境加载方式、固定持久路径、锁定依赖、Python、SQLite、FFmpeg 和字体。
2. 第一次执行 schema 与 ACG 迁移，记录新增、更新、跳过和异常计数。
3. 第二次执行相同迁移，必须零新增、零重复、零角色漂移。
4. 核对生产 `admin` 是 ACG 唯一 owner、其他既有管理员为团队管理员、既有创作者为团队成员、供应商和账号一对一绑定、无孤儿账号/资产、稳定 ID 集合不减少、owner/team/供应商关系摘要不漂移、凭据哈希不变、`quick_check=ok`。新增记录必须单独解释，不能用新增数量抵消记录丢失。
5. 核对媒体相对路径、文件大小和 hash inventory 不减少或异常变化。
6. 分别用目标 release 和兼容回滚 release 做登录、租户隔离、历史数据/媒体读取演练；原始 v120 只做历史基线比较，不作为迁移后可切换回滚版本。

### 阶段 D：版本化发布

1. 从用户确认的本地提交创建干净 detached worktree。
2. 在干净源码中重建无限画布，核对闭包恰为 61 个文件且 manifest 的相对路径、大小和 SHA-256 全部匹配。
3. 使用锁定依赖预建目标 release 和兼容回滚 release 的独立环境，生成只包含代码和静态文件的 release 包；不得使用删除式同步，维护窗内不得联网安装依赖。
4. 部署到新的版本目录，保持旧 release、兼容回滚 release 与 release 外持久数据目录不动；再次核对有效环境不会回落到新 release 内的空路径。
5. 仅通过本文件的唯一 runbook 依次执行正式迁移、启动 loopback sidecar、以强制只读模式启动主服务、通过 readiness，再原子切换 current 指针或流量入口；写入口继续冻结。

### 阶段 E：开放写入前验收

- 服务：主服务、sidecar、单 worker 限制、release/schema 标识一致。
- 数据：业务计数、稳定 ID 集合和 owner/team/供应商关系摘要无异常漂移；新增记录单列解释；媒体相对路径、大小和 hash inventory 无异常减少；SQLite 检查通过。
- 角色：ACG owner/admin/member、个人、外部团队、供应商父/子、游客登录矩阵。
- 隔离：个人与外部团队不能读取 ACG 平台账号、资产、草稿、任务或 Blob。
- 链路：团队申请、供应商首页/全部账号/发布清单、社区、收藏、资产、画布旧草稿恢复、配额成功/失败退款。
- 文件：历史图片可读、视频支持 Range、上传/成片/Blob 路径均可访问。

以上验收必须在强制只读模式完成，GET 不得触发 `_ensure_db()`、状态 heal 或任何隐式写入。目标 release 与兼容回滚 release 均通过后，才按 4.0 的最后一步开放写入。真实付费生成、真实发布或外部消息只在用户另行授权后执行。

## 5. 回滚方案

- **开放写入前失败**：停止目标 release，优先切换到已验证的兼容回滚 release。只有维护窗始终保持全部写入口冻结、能够证明快照后没有任何业务或 runtime 写入，并已验证数据库与媒体快照属于同一一致性点时，才允许整套恢复到生产 v120 快照；否则保留迁移后的数据库并执行前向数据修复。
- **开放写入后失败**：再次冻结写入并先保存事故后数据库和媒体；只允许回滚到理解新 schema、租户隔离、个人/团队账号与配额语义的兼容回滚 release，数据通过前向修复，禁止切回原始 v120 代码，也禁止用旧库覆盖新业务。
- 新迁移默认只扩展，不立即删除旧列/旧表；旧代码必须能忽略新增结构。
- 回滚后重新执行 readiness、SQLite、计数、角色、供应商和租户隔离核验。
- 兼容回滚 release、目标 release 与数据快照必须使用同一 release manifest/迁移兼容矩阵登记；“进程能启动”或“旧版能 SELECT”不等于可安全回滚。
