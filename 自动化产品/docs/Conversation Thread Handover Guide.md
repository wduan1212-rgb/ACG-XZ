## 2. 文档职责与阅读策略

### 每次接手必读

- `运行与架构说明.md`：当前版本、启动方式、架构、数据边界、部署边界和最低验证，是项目当前事实的唯一入口。
- 本次交接消息：本轮完成项、未完成项、验证、风险和下一步。
- 当前 Git 状态：至少检查 `git status --short`、当前分支和最近提交。

### 按需检索，不默认全文读取

- `docs/version.md`：版本历史。默认只读顶部最近 1 至 3 个版本，或搜索交接指定版本、日期和模块；不得把全文阅读设为新线程前置条件。
- `docs/Problem Document.md`：问题与避坑档案。根据本次模块、报错、风险或部署关键词检索相关条目；必要时再向前后扩展上下文，不默认全文读取。
- `docs/Server Deployment Log.md`：真实部署历史。只有部署、回滚、生产核验或报告任务需要读取；默认查看目标版本和最近 3 次部署。
- 具体代码、测试和业务文档：只读取与本次任务直接相关的部分。

## 3. 新线程接手顺序

1. 阅读 `运行与架构说明.md` 和本次交接消息。
2. 执行 `git status --short`、`git branch --show-current`、`git log -5 --oneline`。
3. 读取 `docs/version.md` 顶部最近版本或交接明确指定的版本。
4. 按本次模块和风险关键词检索 `docs/Problem Document.md`。
5. 涉及部署时，再读取目标版本和 `docs/Server Deployment Log.md` 最近记录。
6. 读取本次涉及的代码、测试、diff 和验证结果，再决定后续动作。

不要因为历史文档庞大而一次性装入全部上下文；也不要只依赖聊天记忆绕过当前仓库检查。

## 4. 每次版本迭代的文档维护

每一次形成版本号、提交候选或部署候选的迭代，都必须同步维护以下当前事实：

### 《运行与架构说明》采用覆盖式修订

- `运行与架构说明.md` 是当前状态快照，不是版本流水账。每次修订应更新原有字段和相关段落，直接替换或删除已经失效、重复、与现状冲突的内容，不按版本在文件末尾持续追加说明。
- 文件只保留当前有效的本地版本、线上基线、入口、模块关系、依赖、权限、数据边界、启动方式、部署边界和检查规则。旧版本变化写入 `docs/version.md`，历史问题写入 `docs/Problem Document.md`，真实部署结果写入 `docs/Server Deployment Log.md`。
- 架构没有变化时，替换“当前版本状态”中的版本核对结果并写明“本版架构无变化”；不要保留上一版同类表述形成累积列表。
- 只有新增了仍然有效的模块、边界或长期规则时才允许增加篇幅；相关能力被移除或规则失效时，应同步删掉对应说明，使本文档保持短、准、可直接使用。

1. `docs/version.md`：更新本版范围、验证结果、数据与部署影响、回滚方式。
2. `运行与架构说明.md`：同步更新时间、当前本地版本/构建标识、线上基线，以及本版涉及的入口、模块、依赖、数据、权限、启动或部署变化。
3. 如果本版架构没有变化，也必须更新“当前版本状态”，并明确写明“本版架构无变化”，证明已核对而不是遗漏。
4. `docs/Problem Document.md`：只有遇到明确报错、白屏、交互崩坏、数据覆盖风险、权限串数据、缓存/依赖差异、服务器差异或部署失败时才新增条目。普通功能流水账不写入这里。
5. `docs/Server Deployment Log.md`：只有真实部署完成后才追加实际 commit、资源范围、验证、数据保护和回滚点。

纯问答、只读分析、未形成版本的临时探索，不需要制造版本记录；但如果发现《运行与架构说明》已经失真，应明确指出并在获得修改授权后更新。

## 5. 交接消息必须包含

- 项目路径、仓库、当前分支、最近提交和本地服务状态。
- 当前本地版本、当前线上基线，以及两者是否一致。
- 本轮已经完成的功能、修复、文档或部署动作。
- 已验证内容：命令、测试、接口、浏览器页面、真实生成或发布链路。
- 未验证、验证失败或只能由用户手动确认的部分。
- 当前工作区是否干净；哪些修改属于本轮，哪些是用户或其他线程遗留。
- P0、P1、P2 后续任务。
- 与本轮直接相关的已知坑和规避方式。
- 是否涉及数据库、账号、成员、资产、发布清单、草稿、运行目录、环境变量或服务器配置。
- 新线程需要优先读取的具体文件、版本段落和 Problem 关键词，不要只写“阅读全文”。

## 8. 部署交接规则

部署线程接手前应定向读取：

- `运行与架构说明.md` 中的当前版本、运行、数据和部署边界。
- `docs/version.md` 的目标版本段落，不需要全文读取。
- `docs/Problem Document.md` 中与目标模块、缓存、权限、数据、依赖和部署相关的条目。
- `docs/Server Deployment Log.md` 的最近 3 次部署和目标版本记录。

交接中必须说明：目标 commit、代码/静态资源清单、是否有幂等 schema 增量、备份范围、需要重启的服务、部署后验证和纯代码回滚点。

部署只能更新受控代码与静态资源。不得用本地状态替换生产 SQLite、账号、成员、资产、发布清单、草稿、分析数据、上传、合成文件、画布 Blob、视频工坊 runtime、认证状态或私密配置。回滚恢复代码/静态资源，不得回滚到旧业务数据库。

部署完成后：

1. 在 `docs/Server Deployment Log.md` 追加真实部署结果。
2. 在 `docs/version.md` 目标版本中补充真实 commit、验证和回滚点。
3. 把线上版本基线写回 `运行与架构说明.md`。
4. 只有出现新的可复用问题时才更新 `docs/Problem Document.md`。

## 9. 验收边界

默认只做本次改动需要的关键验收，包括 API、权限、数据写入、真实生成链路、关键交互和针对性测试。只有用户明确要求完整视觉回归时，才扩展到大批截图、全部视口和完整视觉 QA。

自动化测试通过不等于用户已经验收。交接消息必须区分：自动验证、浏览器验证、真实付费链路、生产验证和用户手动确认。

## 10. 线程路由

- 用户指定目标线程时，以用户最新指定的准确名称为准。
- 如果存在多个近似线程名，应先用线程工具确认准确标题，不凭记忆发送。
- 部署线程只负责部署和生产核验；发现代码问题时应把文件、症状、证据和建议修复范围交回代码线程。
- 用户说“先不用动”或“先不做动作”时，接手线程保持等待，不执行文件读取、命令或修改。
